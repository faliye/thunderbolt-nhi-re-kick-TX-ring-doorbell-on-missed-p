# 0001 (re-kick TX ring doorbell) 复评状态 — 2026-07-22

**结论:该补丁所修的症状,极可能是 E2E 信用饿死的表象;根因修掉后它没有对象了。发上游前不要单独提交这一个。**

## 复评依据

1. **症状描述与 E2E 饿死逐字重合**
   0001 的 root cause 写的是"描述符已完全投递(RING_DESC_POSTED、生产者索引有效),但控制器的消费者指针永不前进"。
   而 2026-07-22 确诊:上游 commit `net: thunderbolt: Enable e2e flow control in two direction` 把
   `RING_FLAG_E2E` 也加到 TX 环 → 按 USB4 规范 TX 环开 E2E 就必须先拿到端到端信用才能发 →
   **ASM4242 从不产生这个信用** → 消费者指针永久停住。是同一个现象。

2. **时间线吻合**
   0001 的测试环境写的是 "stock v6.17 nhi/tbnet"。stock tbnet 的 `tbnet_e2e` 默认为 `true`,
   且上述 commit(2025-06 提交)在 v6.17 中已存在 → **当初观察 stall 时 E2E 大概率是开着的**。

3. **实测:根因修掉后,关掉看门狗也不复现**
   配置:`thunderbolt_net e2e_tx=0`(E2E 只给 RX 环,见 0002 补丁)+ `thunderbolt ring_kick_enable=0`(看门狗完全关闭)
   负载:16KB 请求/响应 TCP(与 0001 复现负载同口径)

   | 配置 | 请求数 | stall >50ms | 中位 | max |
   |---|---|---|---|---|
   | e2e_tx=0 + kick 开 | 3000 | 0 (0.00%) | 0.29ms | 0.84ms |
   | **e2e_tx=0 + kick 关** | **6000** | **0 (0.00%)** | 0.31ms | 0.83ms |

   `kick_fires` 在全部 9000 次请求中增量为 **0** —— 看门狗的触发条件("有已投递描述符未被消费")一次都没出现。
   对照 0001 原始数据(0.5~1.7% 往返 stall 200~471ms),6000 次请求本应出现 30~100 次 stall,实测 0 次。

## 实验局限(如实记录)

- 复测时 tbnet 带着本地改动 `TBNET_RING_SIZE=1024`(stock 为 256),且 PCIe MPS 当时为 256(默认 128)。
  这两者理论上都不影响"门铃是否被漏掉",但不是与 0001 原始环境逐位相同。
- 未在 stock v6.17 + e2e 默认开启 的组合下重跑 0001 的原始复现(那会让链路直接不可用)。

## 建议

- 上游只提 **0002**(E2E 不加到 TX 环)。
- 0001 保留在本地作为历史记录;若将来在 `e2e_tx=0` 前提下重新观察到 missed-doorbell stall,再重新评估。
- 0001 的 commit message 中 PCI id 已由 `1b21:1770` 更正为 `1b21:2425`(实测 NHI 的真实 ID)。
